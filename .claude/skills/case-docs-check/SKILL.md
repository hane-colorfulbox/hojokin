# case-docs-check — 案件フォルダの必要書類チェック

案件フォルダを「列挙 → 分類・有無チェック（決定論スクリプト）→ 中身チェック（CC の Read）→
チャット一括報告」の一本道で確認する。**1回の発動でアウトプットまで完走する**のが契約。

## 0. 作業前チェック

### 0.0 {SKILL_DIR} の解決と前提

1. この SKILL.md が置かれているフォルダの**絶対パス**を `{SKILL_DIR}` とする（cwd に依存しない）。
2. `{SKILL_DIR}/review/check_docs.py` が存在することを確認する。
3. `python -c "import openpyxl"` を試す。**無くてもチェック全体は止めない**
   （Excel 構造チェックだけが「要目視」に降格される。check_docs.py が自動で降格する）。
4. 作業フォルダ `{WORKDIR}` を確定する: セッションの scratchpad ディレクトリ
   （無い環境では OS の temp 配下に `case-docs-check-<日付>/`）。
   > 🔴 `{WORKDIR}` 以外にファイルを作らない。**リポジトリ内・案件フォルダ内・Drive は禁止**
   > （DL した顧客ファイルは PII。セッション終了で破棄される場所にだけ置く）。

### 0.1 入力の確定（質問してよいのはここだけ・1回だけ）

| 入力 | 必須 | 取得方法 |
|---|---|---|
| 対象（DriveフォルダURL / 顧客名 / ローカルパス） | ✅ | ユーザー指定 or 会話文脈 |
| 申請枠（通常枠/インボイス枠） | 任意 | フォルダ名サフィックス `_通常枠`/`_インボイス` → ヒアリング様式で照合 |
| 法人 / 個人 | 任意 | ヒアリング様式・登記の有無・決算書種（青色申告/収支内訳書=個人）の多数決 |
| 決算月 | 任意 | PL期末日 → 台帳注記 → 個人は12月固定 |
| 交付申請月 | 任意 | 加点判定用台帳の C3 |
| 対象タスク | 任意 | 既定は「申請書作成＋加点判定」の両方 |

- 対象すら会話から特定できない場合のみ、**最初に1回だけ**上記をまとめて聞く
  （「任意項目は空欄で可。その項目は要確認扱いで進めます」と添える）。
- > 🔴 **チェック開始後は一切質問しない**。判断できない事項は停止せず、
  > 報告の「要確認」「未確定のため要指定」に列挙して完走する（§8）。

### 0.2 コンテキスト自動推定のルール

推定に使った根拠（どのファイルのどの欄か）を必ず報告に併記する。推定同士が矛盾したら
（例: フォルダ名は通常枠なのにヒアリングはインボイス様式）**様式取り違えとして❌最優先**で報告する。

### 0.3 読み取り専用の絶対原則

> 🔴 このスキルは **Drive に何も書かない**。コネクタに `create_file` / `copy_file` 等の
> 書込系ツールがあっても使用禁止。アップロード・移動・共有変更もしない。
> ローカル経路でも案件フォルダへの書込は禁止。成果物ファイルは作らず、報告はチャットのみ。

## 1. 経路A: Drive コネクタで列挙（既定）

手順の詳細は [reference/Drive列挙の手引き.md](reference/Drive列挙の手引き.md)。要点:

1. folderId を確定（URL から抽出、または `search_files` で `NNN.[顧客名]_[枠]` フォルダを検索）。
2. `parentId = '<folderId>'` クエリで再帰列挙。**NFC 正規化後に「申請時使用」サブフォルダは降りない**。
   ページネーションは最後まで取り切る（打ち切りは「不足」の誤報告になる）。
3. 列挙結果を `{WORKDIR}/manifest.json` に保存（name / id / mimeType / parent_path / size）。
4. 列挙自体ができない環境なら、**チェックを開始せず**「ローカルにDLして再実行」を案内して終了
   （開始後の途中停止はしない。pre-flight で判定する）。

## 2. 経路B: ローカルフォルダ

`--local` でスクリプトに直接渡す（列挙・除外・分類はスクリプトがやる）。以降は両経路とも同じ。

## 3. 決定論チェック（1回目）

```
python {SKILL_DIR}/review/check_docs.py --local <フォルダ>            # 経路B
python {SKILL_DIR}/review/check_docs.py --manifest {WORKDIR}/manifest.json   # 経路A
  共通: --task both --entity <法人|個人|不明> --frame <通常枠|インボイス枠|不明>
        --json {WORKDIR}/check1.json
```

- スクリプトは「名前・構造で決まること」だけを判定する（分類・必須充足・拡張子・テンプレ規格・
  ヒアリング様式・SECURITY ACTION「40」始まり）。**日付・年度の意味読みはしない**設計。
- JSON の `findings`（FAIL/WARN/INFO）と `content_check_targets`（中身チェック対象）を読み取る。

## 4. 中身チェック対象のダウンロード（経路Aのみ）

`content_check_targets` のファイルだけを `download_file_content`（base64）で
`{WORKDIR}/files/` に復号保存する（手順は reference/Drive列挙の手引き.md §4）。
- 巨大ファイルの DL に失敗したら粘らず「サイズ超過につき中身チェック省略・要目視」に落とす。
- DL 後に check_docs.py を `--files-dir {WORKDIR}/files` 付きで**再実行**する（2回目）。
  Excel 構造チェック（テンプレ規格・様式判定・未記入）がここで機械判定される。

## 5. 中身チェック（CC の Read）

`content_check_targets` の各ファイルを Read（PDF はページ指定可）で開き、
[checklists/中身チェック手順.md](checklists/中身チェック手順.md) の観点で確認する。
要件の原文・根拠は [reference/必要書類マトリクス.md](reference/必要書類マトリクス.md)。

代表的な確認（詳細はチェックリスト）:
- **履歴事項全部証明書**: 種別（現在事項は不可）／証明日が交付申請日から3か月以内／全ページ
- **納税証明書**: その1/その2か・税目・**対象事業年度が直近決算期と一致するか**（2年前のもの等を検出）
- **決算書**: 期末日と決算月の整合・直近期か・2期分あるか・BS/PL/販管費明細ページ
- **賃金台帳**: 対象12ヶ月＝**直近事業年度**（暦年ではない）か・全員12ヶ月分か
- **見積書**: ツール名がヒアリング「申請ツール名」と一致するか・売上20%超でないか

### 5.1 判定は4値・誤検知防止の降格ルール

| 記号 | 意味 | 顧客への依頼文に載せるか |
|---|---|---|
| ✅ | 中身まで確認して基準を満たす | — |
| ❌ | **確度の高い**不備（不存在・種別違い・明確に読めた年度/日付の不一致・様式取り違え） | 載せる |
| ⚠️ | 疑い・グレー・社内で解決できるもの | 載せない（社内確認リストへ） |
| ❓ | 読めない・情報不足で判定自体ができない | 載せない（情報の追加提供依頼として別枠） |

> 🔴 **読めないものを推測で断定しない**。画像PDF・手書き・低解像度で該当欄が読めなければ❓。
> 「読めた気になった値」で顧客に再取得させるのが最悪の誤検知。

- 非標準様式（給与ソフト独自台帳・非標準法人の登記等）→ 規格チェックは⚠️/❓に降格し、
  目視すべき箇所を具体的に指す。
- 日付境界（登記3か月等）は基準日=交付申請日が未確定なら「実行日基準の仮判定」と明記。
  境界±7日は✅にせず⚠️「申請日次第で失効」。
- 「無いことが正常」なもの（納税額0円・賞与なし・原価報告書なし）は NG 判定の対象外。
- 制度グレー（賞与のみ受給者の除外等）は ⚠️★グレー＋「事務局確認推奨」。断定文言を出さない。
- 同一根本原因（例: 決算月の不一致）から派生する指摘は**1件に束ねる**（指摘を量産しない）。

## 6. 加点判定に必要なものの確認

- 加点判定用賃金台帳（シート『加点判定用明細』）の有無・暦月固定列・C2（都道府県）・
  C3（**交付申請月**。空欄だと加点②判定不能）— check_docs.py が機械判定。
- 決算月≠9月なら加点①の窓が2事業年度をまたぐ → 前期・今期の賃金台帳2冊があるか。
- 賃金状況報告シート（公式様式）の有無。通常枠で補助率2/3希望なら添付必須。
- 医療・介護・社会福祉・学校教育系の法人は賃上げ加点対象外の可能性 → ⚠️で明記。

## 7. セルフレビューゲート

報告を書く前に、**未分類ファイル（UNMATCHED）の名前を全件見直す**:
分類キーワードは表記揺れに弱い（例:「とうきぼ」「登記簿謄本のコピー」「決算資料」）。
必要書類が非標準名で紛れていないか判断し、見つけたら該当カテゴリの判定を修正してから報告する。
迷ったら中身を1ページ Read して確かめる（推測で分類しない）。

## 8. チャット報告（固定テンプレ）

報告はチャットのみ。以下の構成で**一括**出力する（ファイルは作らない）:

```
📋 必要書類チェック結果: {顧客フォルダ名 or フォルダパス}
経路: Drive / ローカル ｜ 対象: 申請書作成＋加点判定 ｜ 走査 {N}ファイル（除外 {M}件）
前提: {枠} / {法人・個人} / 決算月 {◯月 or 未確定} / 交付申請月 {yyyy/mm or 未確定}（根拠併記）
総合: 申請書類 {✅そろっている/❌不備あり} ｜ 加点書類 {✅/⚠️/対象外}

■ 書類別チェック表
| 書類 | 存在 | 形式 | 中身 | 詳細 |
（必須→推奨→加点→提出物の順。各行に検出ファイル名と判定根拠を1行で）

■ ❌ 不備（顧客への依頼が必要）
1. …（何が・なぜダメか・何を依頼するか）

■ 顧客への依頼文ドラフト（❌のみ・コピペ用）
（コードブロックで。要件の言い回しは reference/必要書類マトリクス.md の原文ベースで正確に。
 例: 納税証明書は「その1」または「その2」・法人税・直近決算期分・0円でも可、等）

■ ⚠️ 社内確認リスト（顧客に投げる前に社内で判断）
■ ❓ 判定不能（読めない・情報不足 → 目視 or 追加情報）
■ 未確定のため要指定（交付申請月 等 — 何の判定に効くかを添える）
■ 参考: 除外したもの（申請時使用/、過去のツール出力）・未分類ファイル

※ 本チェックはチャット報告のみでファイルは作成していません。DLした書類は一時フォルダにあり、
   セッション終了で破棄されます。要件の最終確認は公募要領・交付申請マニュアル最新版で。
```

- 依頼文ドラフトには **❌のみ**載せる（⚠️/❓を顧客に投げて不要な再取得をさせない）。
- 各判定に**根拠**（ファイル名・ページ・セル）を必ず付ける。

## 9. 禁止事項・PII・保守

- > 🔴 Drive への書込禁止（§0.3）。チェック結果を管理表・Drive に書き戻さない。
- > 🔴 報告に**従業員個人名・賃金実額**を書かない（書類チェックに不要。台帳は「規格・期間・
  > 人数・該当行数」の観測に留める）。顧客名・ファイル名はチャット報告に限り可。
- DL ファイル・manifest は `{WORKDIR}` のみ。チェック完了後、可能なら削除する（best-effort）。
- 保守: 分類・必須判定の定数は `hojokin/pipeline.py`（FileDetector）・`app.py` からの独立コピー。
  **原本を変えたら `review/check_docs.py` も同時に直す**（`scripts/check_docscheck_sync.py` が
  配布 ZIP ビルド時に AST 突合して不一致なら中止する）。ヒアリング様式・テンプレの改訂時は
  check_docs.py のフィンガープリント／ヘッダー定数を再実測して更新する。
