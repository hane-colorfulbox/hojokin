# 04 賃金台帳の実務と落とし穴

賃金台帳は、補助金の「補助率（最大 2/3）」と「賃上げ計画（R216）・従業員数（R215）」を左右する**最重要の入力データ**です。賃金台帳の数字が過大でも過少でも申請結果がブレるため、回収から変換・検証までを丁寧にやる価値が他の書類より高い領域です。

このファイルは賃金台帳まわりの「やり方」と「典型的な事故」をまとめた実務メモです。制度上の根拠（R215/R216 の定義、加点の仕組み）は [02 制度知識ベース](02_制度知識ベース.md) を、ツールの操作手順は [03 ツールの仕組みと使い方](03_ツールの仕組みと使い方.md) を参照してください。

- R215 = 従業員数（パートは正社員の労働時間に換算した小数値＝FTE。役員・中途者は除外）
- R216 = 給与支給総額（課税対象の給与・賞与等の合計。役員報酬・退職金・福利厚生費・法定福利費は除外）

> ここで言う「FTE換算」は、週20時間のパートを「正社員0.5人分」と数える計算のこと。「課税対象」は給与所得として税金がかかる部分のこと（非課税の通勤手当は含まない）。

## 1. 賃金台帳の回収方針

### 1.1 原則：Excel / CSV でもらう

顧客に賃金台帳を依頼するときは、**原則 Excel または CSV 形式**でお願いします。フォーマットが揃うと、AI に読ませる回数（API コスト）が減り、自動変換の精度も上がるためです。給与計算ソフトの集計エクスポートが理想です。

### 1.2 PDF しか出ない場合の処理経路（2つ・出力は同じ規格）

顧客が PDF しか出せないケースは多くあります。その場合の処理経路は2つあり、**どちらも出力先は同一のテンプレ**（`ツール/賃金台帳テンプレート.xlsx` 形式）です。優先順は次のとおりです。

| 優先 | 経路 | 仕組み | 使う場面 |
|---|---|---|---|
| 1（推奨） | **ツールの「賃金台帳の作成」タスク** | Document AI ＋ Sonnet で PDF を読み取り、ツール規格 Excel に自動変換（Streamlit Cloud 上で実行） | まずこれを試す。テキスト主体の PDF など |
| 2（フォールバック） | **Claude Code のスキル `wagebook-convert`** | 手元の Claude Code が PDF を読んで規格 Excel に変換 | 経路1が失敗した場合・手書き PDF・画像 PDF など精度が落ちる PDF |

- 経路1で Sonnet の画像フォールバックは精度面で劣るため無効化済みです。Document AI が失敗した・手書き PDF で精度が落ちた場合に、経路2（スキル）へ回します。
- 経路1（ツール）と経路2（スキル）は**実装は独立しています**が、**出力規格は同一**（同じテンプレ列・同じ補助金ルール）です。

### 1.3 規格を変えたら両方を同期する（重要な運用ルール）

出力規格（テンプレの列構成・補助金ルール）を変更・追加したら、**ツール側とスキル側の両方を差分チェックして同じく直します**。片方だけ直すと、スキルが作った成果物をツールが正しく読み込めなくなります（過去に T列「年間賞与」を追加したときは、ツール・スキル両方のテンプレと配布 ZIP を同期しました）。同期の正本ルールは `補助金/CLAUDE.md`「賃金台帳の回収方針」にあります。

## 2. wagebook-convert スキルとは

`wagebook-convert` は、PDF（テキスト／画像／手書き）または既存 JSON の賃金台帳を、ツールが読み込める**規格 Excel** に変換する Claude Code 用スキルです。経路1（ツール）で自動化が失敗したときのフォールバック手作業を担います。

### 2.1 何をするか

- PDF を Read ツールで直接読み取り（multimodal）、氏名・雇用形態・各月の課税支給合計を抽出する
- 役員ラベルの正規化（後述）、直近事業年度12ヶ月の正しい月配置、通勤手当の別欄処理、パート時間の取得（FTE換算用）といった**落とし穴を回避する手順**を内蔵している
- `templates/賃金台帳テンプレート.xlsx` を openpyxl でコピーして書き込み、`{会社名}_賃金台帳一覧.xlsx` を出力する
- 出力前に機械検算スクリプト（`review/verify_wagebook.py`）と PDF 突合のレビューゲートを通す

### 2.2 いつ発火するか

- ユーザーが「賃金台帳を変換して」「PDF の賃金台帳を Excel にして」「賃金台帳テンプレートを埋めて」等と依頼したとき、自動で発火する
- 明示的に `/wagebook-convert` で起動することもできる
- 入力は手書き台帳・画像 PDF・テキスト PDF・既存 JSON のいずれでもよい

### 2.3 着手前に必ず取得する情報

スキルは作業前に次を確認します（引き継ぐ人もこの観点を押さえておくと事故が減ります）。

- 元データ（PDF パス／アップロードファイル名／既存 JSON）
- 会社名（出力ファイル名に使う）
- **決算月（1〜12 の数字）**：事業年度の並べ替えに必須。指定漏れは事故率が高い
- 法人／個人事業主の別（個人事業主は「事業主」「専従者」の扱いが特殊）
- 履歴事項全部証明書 PDF（あれば役員自動判定の精度が上がる。任意）
- 賃金台帳が単一 PDF か複数 PDF か
- （非暦年決算では実質必須）賞与の各回の支給年月

配布は ZIP（`scripts/build_skill_zip.py` で生成 → Drive 経由で他担当者へ）です。

## 3. 5つの典型的な落とし穴

賃金台帳変換でくり返し起きる事故です。いずれも「症状 → なぜ起きる → 対処」で整理します。

### 落とし穴 (1) 月列の左詰めズレ（最頻出）

**症状**：途中に支給のない月（空欄）がある社員で、空欄以降の月を1つずつ詰めてしまい、全部が1ヶ月ズレる。さらに末尾2ヶ月を1セルに合算してしまう。

| | 1月 | 2月 | 3月 | 4月 | 5月 | 6月 |
|---|---|---|---|---|---|---|
| 正（PDF） | A | （空） | B | C | D | E |
| ❌誤（左詰めズレ） | A | B | C | D | **D+E合算** | （空） |

**なぜ起きる**：PDF の並びを「左から順に詰めて」転記すると、空欄月をスキップして以降がズレる。さらに厄介なのは、**月をずらしても年間合計は変わらない**こと。実案件で、正しい配置とズレた配置の年間合計が完全に一致したため、年間合計の照合では見逃された。

**対処**：

- G〜R 列の「1月〜12月」には、暦年ではなく**対象会社の「直近事業年度」の12ヶ月**を、**それぞれの支給月のカレンダー列に1セルずつ対応付けて**入れる。空欄月はそのまま空欄にし、後続を詰めない。
- セルのラベルはカレンダー月のままでよい（ツール側が決算月から事業年度順に並べ替える）。値だけを正しい月位置に置く。
- 検出は年間合計だけでは不十分。月別全社計との照合（5-B）や、空欄月のある社員を PDF と1セルずつ突き合わせる月単位検算（5-M）が必須（後述の §4）。

> 補足：12月決算（事業年度＝暦年）の会社ではこのズレは起きない。3月・4月・6月・9月決算などでのみ注意。

### 落とし穴 (2) 役員ラベルの正規化漏れ

**症状**：「代表取締役」「取締役」などの役職名をそのまま転記したために、本来 R216 から除外すべき役員報酬が算入されてしまう。

**なぜ起きる**：ツール側の役員判定は、雇用形態の文字列に**「役員」という文字が含まれるか**だけで行っている。役職名のままだとマッチせず、除外されない。

**対処**：雇用形態を次のとおり正規化する。

| 元 PDF の表記 | 正規化 |
|---|---|
| 代表取締役 / 取締役 / 監査役 | **役員**（R215・R216 から除外） |
| 理事長 / 理事 / 監事（医療法人等） | **役員** |
| 事業主 / 個人事業主（個人事業主テンプレ時） | **役員**（R216 から除外） |
| 専従者 / 青色事業専従者（個人事業主） | **正社員**（R216 に算入） |
| パート / アルバイト / 非常勤 | **パート・アルバイト** |
| 現場代理人 / 主任 / 営業 など職位名 | **正社員** |

役職欄が空欄のときは、(a) 履歴事項全部証明書があれば役員氏名を照合して「役員」に置換、(b) 無ければ「会社名と同姓／月額が完全一定／月額が極端に高低／社員番号が他と不連続」のいずれか（OR 条件）に当たる人を**役員候補**としてメモに残し、最終判定は顧客確認に委ねる。

注意点：

- 履歴事項証明書には**辞任・退任済みの役員も載る**（抹消線・「辞任 令和N年M月D日」付き）。これらは現役ではないので除外し、台帳に載っていれば「正社員」として扱う。「重任」「再任」は継続中。
- 医療法人では**理事長のみ登記され、他の理事・監事が登記されない**ことがある。登記が無い＝いない、ではない。
- 履歴事項に役員がいても**賃金台帳に氏名が無い**ことがある（役員給与が別管理 or 無報酬）。この場合は台帳の全員を「正社員」にし、その旨を警告メモに残して顧客確認とする。

### 落とし穴 (3) 通勤手当の二重控除（S列の扱い）

**症状**：月列に「課税支給合計」を入れたうえで、S列「年間通勤手当」にも値を入れてしまい、R216（給与支給総額）が通勤手当の分だけ過少になる。

**なぜ起きる**：「課税支給合計」は非課税の通勤手当を**すでに除外済み**。それなのに S列を埋めると、ツールが在籍月数で均等割して通勤分を**もう一度**減算する。配布テストの3案件すべてで発生した。

**対処**：列構成で判断する。

| ケース | G〜R 列（月列） | S 列「年間通勤手当」 |
|---|---|---|
| 台帳に「課税支給合計」列がある | その値を転記 | **空欄（厳守）** |
| 「合計（通勤費込み）」列しか無い | 合計列をそのまま転記 | **非課税通勤手当の年間合計**を入れる（ツールが在籍月数で均等割減算） |

S列を埋めてよいのは「合計（通勤費込み）」しか列が無く、それを月列に入れたときだけ。検算は「Σ(G〜R) + T列年間賞与 = PDF の課税年間合計」が成立するのに S列にも値があれば二重控除（§4 の 5-F）。

### 落とし穴 (4) 暦年 vs 事業年度の取り違え

**症状**：PDF が暦年（1〜12月）で出ているのをそのまま入れると、事業年度と半年〜数ヶ月ズレた金額で R215/R216 が集計される。

**なぜ起きる**：給与計算ソフトは暦年区切りで出力することが多い。一方ツールは決算月から事業年度順に並べ替えるため、入れる値も「直近事業年度の各月」でないと意味がズレる。

例（4月決算 → 直近事業年度＝2024年5月〜2025年4月）：

| 決算月 | xlsx の各列に入れるべき期間 |
|---|---|
| 12月 | 暦年と一致（2024年1月〜12月） |
| 4月 | 2024年5月〜2025年4月 |
| 3月 | 2024年4月〜2025年3月 |
| 9月 | 2024年10月〜2025年9月 |
| 6月 | 2024年7月〜2025年6月 |

**対処**：

- 決算月が暦年始まりでない会社では、**2つの暦年 PDF をまたいで12ヶ月を抜き出す**必要がある（例：4月決算なら「5月〜12月」は前年の暦年 PDF、「1月〜4月」は当年の暦年 PDF から）。
- 決算月が不安なら、PDF 先頭の期間表記から逆算できる（年間集計表が「令和6年12月→令和7年11月」と並んでいれば先頭月＝事業年度開始月＝決算月+1）。
- PDF が暦年で、事業年度が暦年でない場合に**事業年度の前半6ヶ月が PDF に無い**構造（例：6月決算で TKC の暦年出力）になることがある。このときは原則 (C) 事業年度に合致した PDF の再取得を顧客に依頼する。やむを得ず暦年データで進める場合は B2 セルに大きく警告を残し、報告に明記する。
- 「全月在籍なのに台帳の窓が1ヶ月だけズレて欠けた人」は、公募要領上は算定対象に含めるべき人。中途者として除外してはいけない。まず窓を正しく取り直す。逆に**本物の中途採用・退職者**（全月分の給与を受けていない人）は除外（空欄のまま）し、按分で水増ししない。

### 落とし穴 (5) 非暦年決算の賞与の帰属年度

**症状**：賞与の支給月が台帳に無く（「令和N年X回」など回数表記のみ）、決算月が12月でない場合に、「○回目＝夏＝窓内」のように回数から帰属を**推測で確定**してしまう。実案件（8月決算）で、推測確定が別経路の算定と1人あたり数十万円ずれた事故が起きた。

**なぜ起きる**：決算月が12月でないと事業年度の窓が暦年とズレるため、支給月が分からない限り「どの回が窓内か」は確定できない。

**対処**：次の3条件が揃ったら**推測で確定しない**。

1. 決算月 ≠ 12月、かつ
2. 台帳に賞与の支給年月日が無い、かつ
3. ユーザーから支給月の指定も無い

このときは、

- T列は最も妥当な暫定セット（一般に「直近の冬賞与＋直近の夏賞与」）で埋め、該当セルを黄色にする
- B2 セルと完了報告に「賞与の支給月が未記載。事業年度内の賞与を確定するため (a) 各賞与回の支給年月、または (b) 勘定科目内訳明細書（人件費内訳＝法人 R216 の正式ソース）を提供してください。現状 T列は暫定（含めた回／除外した回）」と明記する
- 「他回は対象外」と断定しない

逆に、決算月＝12月／支給年月が台帳にある／ユーザーが支給月を指定した、のいずれかなら確定してよい。

> なお賞与は **R216 に含める**が、**月セル（G〜R）には混ぜず T列「年間賞与」に年間合計**で入れる。月セルに混ぜると最低賃金判定（加点）や直近月の月額が歪み、ツールが認識できない。

## 4. レビューゲート（提出前の人手確認）を飛ばさない

### 4.1 なぜ飛ばしてはいけないか

賃金台帳の抽出精度は**補助率 2/3 を左右**します。R216 を過少に見積もると賃上げ計画が未達リスクになり（年平均成長率が0以下だと全額返還）、過大に見積もると後年の効果報告で説明不能になります。one-shot 出力で最も起きやすい事故（S列二重控除・月配置ズレ・賞与混入・パートFTE/役員混入）は、このゲートで止めます。最賃ギリギリ層は原本照合が必要です。

### 4.2 ゲートの中身（要点）

レビューは「作った本人の見直し」では確証バイアスが残るため、**別人格のレビュアーに切り替えて**、作業メモを見ず PDF を真として粗探しします。

1. **機械検算スクリプトを実行**：`python .claude/skills/wagebook-convert/review/verify_wagebook.py "{会社名}_賃金台帳一覧.xlsx"`。openpyxl のみで動き、API は使わない（他人の PC でも動く）。出力を完了報告に貼る。
   - **FAIL（修正必須）**：役員ラベル未正規化／パートで E列空欄／全月在籍の非役員が0名／注記付きで読めない月ヘッダー（FLAG-H）→ xlsx を直して再実行
   - **要確認**：FLAG-S（S列に値）／賞与混入候補／月セルの0 → PDF で素性を確認して判断を報告に明記
2. **PDF との白紙突合**（機械では決められない意味照合）：
   - 月配置ズレ：縦計が合っても OK ではない（左詰めズレは年間合計を素通りする）。**途中に空欄月のある社員は全員＋無作為3名**を PDF と各月1セルずつ突合する
   - S列：月列が「課税支給合計」由来なら S列を空に、「合計（通勤費込み）」由来なら S列保持が正
   - 賞与候補：突出した月を T列へ分離したか、繁忙期残業・歩合で月セルのままが正か確認

### 4.3 検算チェックリストの要点（checklists より）

提出前に必ず通すチェックリスト（`checklists/validation_checklist.md`）の要点です。

- **A. 対象期間**：1月列が直近事業年度の範囲内か。5月・6月など事業年度開始月の列が前年同月になっているか。暦年データをそのまま入れていないか。
- **B. 雇用形態**：役員系が「役員」に、職位名が「正社員」に、パート系が「パート・アルバイト」になっているか。辞任役員を除外したか。
- **C. 金額**：G〜R が「課税支給合計」由来か（賞与は含めない）。差引支給額を誤採用していないか。賞与は T列に年間合計で入っているか。非暦年決算で賞与の帰属を推測確定していないか。
- **D. 通勤手当（S列）**：月列に課税支給合計を採用したら S列は空欄か（二重控除チェック）。
- **E. 中途入退社者**：退社月以降が0でなく空欄か。窓ズレで1ヶ月欠けた全月在籍者を中途扱いしていないか。全月在籍の非役員が0名になっていないか。
- **F. ファイル名・体裁**：`{会社名}_賃金台帳一覧.xlsx`、シート名「従業員別明細」、ヘッダー5行目、月見出しに注記なし（注記すると0名誤読）、データ行 B6 から、数字が文字列扱いでないか。
- **H. 検算（複数アプローチ・必須）**：5-A 社員ごとの年間合計、5-B 月別全社計の横断、5-M 月単位の1セル突合（空欄月のある社員は全員＋最低3名）、5-C 総合計シート突合、5-E OCR 1円誤差の正規化、5-F S列二重控除チェック。**年間合計だけで終わらせない**（月ズレは年間合計を素通りする）。
- **G. 手書き・画像PDF**：B1〜B3 に赤字警告、信頼度の低いセルを黄色強調、変換メモシートに不明瞭ページを記録、報告に「人による全数値照合が必須」を明記。

手書き・低解像度で読み取り困難と判定したら、その場で作業を停止し、顧客に代替ソース（給与計算ソフトの集計 CSV/Excel が最推奨、次に高解像度スキャン、最後の手段が人手転記）を打診します。「最低限動く」より「プロダクション品質」を優先します。

## 5. 加点判定は別物（標準台帳とは作り直す）

賃上げ加点（項目14/15）の判定は、ここまで説明した R215/R216 用の標準賃金台帳とは**別の専用台帳**が必要です。混同に注意してください。

- 加点判定は**2工程**：①実行タスク「加点判定用賃金台帳の作成」で専用台帳を作る → ②実行タスク「加点判定」でその台帳から判定する
- **R215/R216 用の標準台帳は加点判定に使えない**。加点は「時間換算給与＝基本給÷月間所定労働時間」を暦月固定で見るため、総支給ベースで基本給・所定労働時間・暦月固定列を持たない標準台帳では正社員が判定からこぼれる
- 専用台帳の月列見出しは「YYYY-MM」の暦月固定（標準台帳の事業年度順とは並べ方が違う）
- 都道府県は会社で1つ、役員は判定母数から除外、交付申請月の入力が必須

詳細な制度根拠（時間換算給与の定義、暦月固定の期間、補助率引上げとの関係）は [02 制度知識ベース](02_制度知識ベース.md) を参照してください。
