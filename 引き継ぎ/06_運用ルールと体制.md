# 06 運用ルールと体制

## 第7次以降の適用（2026-11-05 更新）

第7次（第7回公募）以降の案件は、まず [第7次申請 担当者向け要点](../docs/第7次申請_担当者向け要点.md) を読む。詳しい根拠は [変更点と使い方](../docs/第7次申請_変更点と使い方.md)、[公式資料で判断できることと確認の範囲](../docs/第7次申請_公式資料で判断できることと確認の範囲.md)、[確認待ち事項](../docs/第7次申請_確認待ち事項.md) にある。

- 給与の0年度目（交付申請日の属する事業年度）は見込み値で入力する。窓口担当が事務局に照会して確認済み。
- 給与0年度目の見込みと、労働生産性の基準になる前事業年度の実績は、別のデータとして集める。
- 過去の交付歴・従業員への表明・対象人数・根拠は、確認した事実だけを使う。分からないものはAIで埋めず、確認できるまでその数値を確定しない。
- 効果報告で何と比べるか（申請時の見込みか確定実績か）は未確定。今回の対応は申請までとする。

以下の加点条件は第7次以降用。第1〜6次（旧回）の訂正・再出力には旧版の様式とルールを使い、公募回・実際の申請月・原本の版を明記する。過去の検証日・会議での発言・実装の経緯は当時の記録で、第7次の要件の裏取りには使わない。

このパックの他のファイルが「補助金とは何か」「ツールはどう動くか」を説明するのに対し、ここは **業務をどう回すか**（だれに聞くか、何を漏らしてはいけないか、どう公開・送信するか）をまとめる。技術より先に、まずこのルールを押さえてほしい。

関連: 索引は [00 はじめに](00_はじめに.md)。賃金台帳の依頼方法の詳細は [04 賃金台帳の実務と落とし穴](04_賃金台帳の実務と落とし穴.md)。

## 1. 連絡窓口は一本化する

賃上げ申請（補助金）に関する指示・依頼は、**営業窓口担当者（窓口）を経由して受ける**のが原則。

- 他のメンバー（たとえば製品側・API管理側）から個別に依頼が飛んできた場合でも、**いったん営業窓口担当者に集約してから動く**。
- これは1次申請の振り返りミーティング（2026-05-14）で、依頼経路がばらつくと混乱が起きると分かったため、**混乱回避を目的に一本化**したもの。
- 引き継ぐ人へ: 「誰から来た依頼か」ではなく「窓口に集約されているか」で判断する。直接依頼に即応するのではなく、まず窓口に通す癖をつける。

## 2. 顧客への賃金台帳の依頼方針（原則 Excel / CSV）

賃金台帳（従業員の月々の給与をまとめた帳簿。補助金の従業員数・給与総額の算定に使う）を顧客から回収する際は、**原則として Excel / CSV 形式で依頼する**。

- 理由: フォーマットを統一できると、AI 抽出にかかる費用（API コスト）を節約でき、自動化の精度も上がるため。
- PDF しか出てこない場合の処理経路（ツール側の自動変換 → 失敗時は手元の変換手順）と、その落とし穴の詳細は [04 賃金台帳の実務と落とし穴](04_賃金台帳の実務と落とし穴.md) を参照。
- ツール経路と手元の変換手順は実装は別だが **出力規格は同一**。規格（テンプレートの列・補助金ルール）を変更したら、必ず両方を差分チェックして同じく直す（片方だけ直すと、変換した産物がツールに正しく読み込まれなくなる）。

## 3. 資料・ドキュメント作成方針

読み手は **非エンジニア（経営者・顧客）** を想定する。

- 技術用語はそのまま使わず、**業務上のメリットに言い換える**。
- 提案資料は「これをすると何が改善されるか」が **1文で伝わる**ように書く。
- 会議メモ・議事録は **決定事項・宿題・担当者・期限** の4点を必ず含める。
- 提案資料・マニュアルなど、顧客や経営者が直接読む成果物は、この方針で作る。
- ツールに手を入れたこと・運用ルールを変えたことを社内へ報告するときも、この方針でまとめる。

## 4. 機密情報の取り扱い

顧客の情報と認証情報の漏洩は実害が大きい。**最初から入れない**のが基本方針（後から消すより確実）。

### 案件の作業で顧客データを Claude に渡すとき

賃金台帳・決算書・ヒアリングシートなどの顧客データは、案件の作業のためなら claude.ai のチャット・Cowork・Claude Code に渡してよい。そのときは次のルールを守る。

<!-- customer-data-rules:begin -->
**顧客データを扱うときのルール（チャット・Cowork・Claude Code 共通）**
- 1案件＝1会話で作業する（チャットは1チャット、Cowork は1タスク、Claude Code は1セッション）。別の案件の資料を同じ会話に混ぜない。
- claude.ai のチャットでは、シークレットチャットが使えるならそれを使う。
- 成果物をダウンロードするか Drive に保存したら、チャット・Cowork の会話は削除する。
- 会話の共有リンク、Project への添付、アーティファクトの公開はしない。
- 作業メモ・ログ・修正依頼には、顧客名・従業員名・金額を書かない（「顧客企業A」「従業員B」などに置き換える）。
<!-- customer-data-rules:end -->

### 開発リポジトリの扱い（ツールを改修する開発担当向け）

ツールのリポジトリは「いつ public になっても困らない状態」で運用する。以下はリポジトリにコミットするときのルール。

### コミットしてはいけないもの（明確に禁止）

- 顧客企業名（実名）→「顧客企業A」「クライアント1」等の汎用記法に置換する
- 顧客従業員の氏名・連絡先・住所・電話番号・メールアドレス
- 給与額・年収・賃金台帳の金額（実数値）
- APIキー、トークン、サービスアカウント鍵（JSON 含む）
- 顧客実データ（ヒアリングシート、決算書、賃金台帳、給与明細など）→ 原則 `.gitignore` 配下に置き、バージョン管理の対象にしない

### 環境変数へ逃がすことが望ましいもの

- Google の Sheet ID / Drive フォルダ ID / Webhook URL
- 社員メールアドレス
- これらは機能上必要ならコード内に置くこともあるが、可能なら環境変数（`.env`）や Apps Script のプロパティに逃がす。コードへのハードコードは避ける。

### コミット前に必ず確認すること

1. ステージング内容（`git status` と `git diff --cached`）を実際に見る
2. ファイル名に「資料/」「決算」「賃金」「給与」「明細」「ヒアリング」が含まれていたら除外する
3. 上記「コミットしてはいけないもの」が混入していたら、止めて確認する
4. コミットメッセージにも顧客名・固有名詞を書かない（「顧客企業」「対象会社」等で抽象化する）

### 既存の防御層（このリポジトリで整備済み）

- `.gitignore` — 顧客資料・認証情報・`.env` を除外
- `.gitleaks.toml` — 顧客名・社員メール・特定金額を検知
- `.git/hooks/pre-commit` — コミット時に自動スキャン

push 前の自己問答として「このコミットが GitHub の public で見えてしまったら困らないか」を必ず一度考える。グレーゾーンで迷ったら、確認してから進める（確認コストより漏洩対応コストの方が高い）。

> 補足: 顧客実データの抽象化（「ある案件では」「顧客企業A」等）は、コミット内容だけでなく、この引き継ぎ資料を含むすべての作業ログ・メモにも適用する。

## 5. 本番デプロイとロールバック

書類作成ツール（`app.py`）は **Streamlit Cloud で本番運用**している。ローカルで Streamlit を立てているわけではない。

- **デプロイ手順は `git push` のみ**。Streamlit Cloud が GitHub の `main` ブランチへの push を検知して **自動で再デプロイ**する（通常1〜2分）。
- 「再起動」「Ctrl+C して起動し直し」「キャッシュ削除」などのローカル操作は不要。push すれば反映される。
- **ロールバック**は次のいずれか:
  - `git revert`（問題のあるコミットを打ち消す）
  - Streamlit Cloud 側の設定（secrets）での **機能フラグ切替**（特定機能を ON/OFF する変数で旧挙動に戻す）

注意点として、Streamlit Cloud のログのタイムスタンプは UTC 表記。日本時間に直すには **+9時間**して読む。

## 6. メッセージ送信（メール / Slack 等）の手順

メール・Slack・PR や Issue のコメント等の送信を依頼された場合、業務の一環として送信そのものは進めてよい（依頼自体が承認に当たる）。ただし手順は守る。

1. **下書きを提示する**
2. 修正指示があれば反映する。何も言われなければそのまま送信する
3. 送信後は **送信先・件名・送信時刻を必ず報告**する

例外として、次のいずれかに当たる場合は、下書きを提示したうえで **明示的に確認を取ってから**送信する。

- 送信先が **新規**（過去にやり取りのない相手）
- **社外** への送信
- **センシティブな内容**（クレーム、契約、料金交渉など）

## 7. 毎年の定期更新（最低賃金の改定）

地域別最低賃金の改定額は例年夏に答申され、**発効日は都道府県ごとに違う**（令和7年度改定は2025年10月〜2026年3月、令和8年度改定は2026年10月〜12月に分かれた）。加点①の上限（令和8年度改定額）、各月に適用される法定の最低賃金、申請画面の表示額は、それぞれ別の値として扱う。改定を取りこぼすと古い値のまま資料を出す事故になる（実際に、ある案件で加点②シートの内蔵最賃マスタが前年度＝改定前の値のままで、直近月に適用すべき改定後の値が表示されず先方から指摘を受けた）。

改定額と各県の発効日が公表されたら、次を確認・更新する。

1. ツールの最低賃金マスタ（額と発効日）を、厚生労働省・各労働局の一覧と **全47都道府県で照合**する（開発担当の作業）。旧回の値は消さずに残す。
2. 公式の加点様式（①②）は **原本を直さない**。差し替えるのは、事務局が様式の更新版を出したときだけ。
3. 第7次の公式②の「最低賃金マスタ」は令和7年度の値1つだけで、基準月（令和8年6月）にも直近月にも同じ値を表示する。直近月が令和8年度改定の発効後でも、令和7年度の額が出る（例：東京は1,226円と表示されるが、法定は2026/10/1から1,280円）。この場合は、適用した法定額と発効日を説明メモに書いて提出物に添える。
4. 公式②のマスタには厚労省の一覧と違う箇所もある：秋田の発効日（様式は2026/3/1、正しくは2026/3/31）、福島の発効日（様式は2025/1/1、正しくは2026/1/1）、広島の発効日（様式は2025/12/1、正しくは2025/11/1）、山形の金額（様式は1,031円、正しくは1,032円。公式①のマスタは1,032円で正しい）。これも原本は直さず、該当する案件では説明メモで補う。
5. 公式②で Excel の「データ」→「すべて更新」は実行しない。表示用のマスタが隠しシートの古い値（令和6年度）を読み込み直す作りのため、表示が古い値に戻るおそれがある（Excel での実行確認はしていない）。数式の再計算とは別の操作。

補足：様式の最低賃金欄は加点②の合否に使われない（合否は事業場内最低賃金の2時点の差が55円以上かだけ）。ただし表示が実態と違うと事務局の疑義を招くので、説明メモで補う。ツールが加点を自動判定できるのは事業場が1つの県だけの案件。派遣業など勤務地が事業所所在地と異なる場合や、事業場が複数県にある場合は個別に確認する（[05 実案件から得た教訓](05_実案件から得た教訓_抽象化.md) の ★グレー参照）。
