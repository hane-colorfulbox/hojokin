# 05 実案件から得た教訓（抽象化）

実際の交付申請MTG、社内のツールフィードバック、事務局との整合確認から得た「別の案件でも再利用できる事実・教訓」を集めたファイル。元になった案件メモ・MTG文字起こしは社外秘（非配布）なので、ここでは**顧客名・個人氏名・実額をすべて落とし、役割表現・一般化した形**で残している。

制度の根拠は [02 制度知識ベース](02_制度知識ベース.md)、賃金台帳の手順は [04 賃金台帳の実務と落とし穴](04_賃金台帳の実務と落とし穴.md) を参照。

> ⚠ 事務局未確認の「グレー解釈」には ★グレー を付けている。これらは「我々が現時点で事実と認識しているが、事務局に照会すると変わりうる」もの。実案件で当たったら優先的に事務局確認する。

## 1. 交付申請（申請ポータル）の実務知識

### 申請ポータルは3フェーズ構造で、入力主体がバトンタッチする

- フェーズ①：申請者（顧客）が基本情報・財務・添付などを入力 → 完了で支援事業者へ引継ぎ。
- フェーズ②：支援事業者がITツール情報・補助金額を登録。
- フェーズ③：申請者が計画数値・賃上げを入力し、SMS認証で提出。
- 支援事業者は、顧客のGビズIDでログインした画面を画面共有しながら一緒に進めるのが基本。

### 申請枠によって入力項目が変わる

- 通常枠は、給与支給総額に加えて「労働生産性指標」（営業利益・人件費・減価償却費・総労働時間の3年計画、年平均成長率3%目標）を入力する工程が追加される。
- インボイス枠は給与支給総額が中心で、この工程はない。
- 会社の状況（設立時期・在籍期間・前回申請の有無）でも工程が変わる。画面に出た項目をその場で埋める前提で進める。

### 申請MTGの前にそろえる事前準備物

冒頭で点検すると進行が速い。必須確認物：

- GビズIDプライムでログインできるか（アプリ認証は事前設定が要る）。
- IPA SECURITY ACTION 自己宣言ID（5から始まる11桁）。
- IT戦略ナビwith の結果PDF。
- 添付書類（履歴事項全部証明書・法人税納税証明書・損益計算書）。
- 賃上げ表明の記録、賃金台帳。

SECURITY ACTION 自己宣言IDはヒアリングで取りこぼしやすく、未記入だとMTG冒頭で探す羽目になる。事前ヒアリングでこのID欄を必ず埋めてもらう運用にする。GビズIDの画面とIPA SECURITY ACTIONの画面は別物なので、顧客が混同しないよう別途リンクを案内する。

### 添付書類の形式要件

- 各10MB未満、形式は .jpg / .jpeg / .png / .pdf のみ。
- 履歴事項全部証明書は発行3ヶ月以内かつ全ページ。サイズ超過時はコールセンター案内。
- 最終確認画面では「添付ファイルは必ず全て開いて内容確認」の指示がある。
- 当日に正式版が未取得でも、添付必須欄が空だと先へ進めない。前回提出分など手元の書類で**仮添付して入力を進め、後日正式版に差し替えて提出**するパターンが有効（納税証明書の翌日差し替え等）。

### 前回申請・別回次の残骸の処理

- 申請者メニューの交付申請情報詳細に前回作成分や別回次の残骸が残っていると破棄が必要。
- 手順：採択通知を開く → 下部のGビズID連携解除 → ログアウト → 招待メールのURLから再ログイン → マイページ再開設。
- MTG前に作りかけ・別回次の申請が残っていないか事前確認しておくと冒頭で詰まらない。

### 事業内容（255文字以内）

- 支援事業者がヒアリングを基に作成し、MTG中にチャットで送って顧客に貼り付けてもらう。
- 法人番号 → 「情報取得」で事業者名等の一部は自動補完されるが、残りは手入力。

### 役員情報と登記の照合

- 役員情報は履歴事項全部証明書（登記）と照合が必要。監査役を含めて役員数を数える。
- 退任役員が登記に残っていれば申請にも反映が要る。登記を後日修正する場合は申請情報も修正が必要になる点を顧客に伝えておく。

### 宣誓・確認画面のクセ

- 初回は「不正行為にご注意ください」ページで【確認完了】を押さないと先へ進めない。
- アンケートは「審査には影響しないが入力必須」の設問が多く飛ばせない。
- 補助事業者登録の申請要件確認は27項目前後のチェックリスト。過去に交付を受けた者には賃金引上げ要件（1人当たり給与支給総額の年平均成長率を物価安定目標+1.5%以上で3年計画）の宣誓が含まれる。

### 編集ロックと推奨ブラウザ

- 支援事業者の入力完了後は内容の変更・編集ができなくなる旨の警告がある。フェーズ②へ引継ぐ前に再確認する。
- 推奨ブラウザは Edge / Chrome 最新版。

### 最終提出（SMS認証）

- 最終提出はSMS認証。認証コードは発行から30分間有効なので30分以内に提出する。
- SMS番号は提出者の携帯（代表者の番号等）になることがある。本人がその場にいなければ提出だけ後日に回せる（入力内容は保存される）。
- 後日提出：申請マイページ → 交付申請情報詳細 → 「次へ」で該当画面まで進み、差し替え/認証コード発行 → 提出（再ログイン不要なこともある）。

### 申請MTGの運営のコツ

- 数字・文章はチャットで1つずつ送ってコピペしてもらい入力ミスを防ぐ。
- 支援事業者の入力フェーズ（ITツール・金額）は顧客にマイク/カメラオフで5〜15分待機してもらう。
- 金額サマリは顧客と読み合わせて、内訳と申請額の認識相違を確認する。
- 提出前に賃金台帳ベースで給与支給総額を検算する。
- 最後に締切・審査期間・交付結果発表日を説明して終える。初回1社の所要は約60〜76分。

## 2. 給与支給総額・FTE まわりの実務判断

制度定義は [02](02_制度知識ベース.md) に集約。ここでは実案件で実際に判断に迷った/ヒヤリした論点を残す。

### R216 の対象者と転記元

- 対象者は前事業年度の1年間に給与支給を受けた者のみ。退職済みでも前事業年度に全月給与を受けていれば対象に含める。
- 転記元は **課税支給合計**（給与所得として課税対象となる額）。手取り（差引支給額）でも通勤費込み総支給でもない。非課税通勤手当は除く。
- 前年度実績と計画値を入れたら「年平均成長率計算」ボタンで自動計算される。

### 「総支給／課税対象額／差引給与額」の呼び替えヒヤリ

- MTG中に口語で「差引給与額でいいか」「課税対象額」「総支給額」と言い直して違う列を拾うヒヤリが実際に起きる。
- 対策3点を手順化する：①転記元は課税支給合計列に固定 ②非課税通勤手当のある従業員では総支給と差が出る点を注記 ③最後にツール出力の値とポータル入力値を突合する。
- 通勤手当のない人では総支給＝課税支給合計で実害が出ないため見過ごしやすい。

### 支給日ベース台帳の「窓ズレ」

- 賃金台帳が支給日ベース（「○月支給分」＝翌月払い）だと、事業年度の最終月分が翌期支給になり、台帳上11ヶ月分しか現れず事業年度と1ヶ月ズレることがある。
- 実際には全期間在籍のケースがあるので、対象月の取り方を必ず確認する。**台帳の月数が少ない＝中途者と即断しない**。入退社日で実在籍を確認する。
- 期間外になった月の金額は、原則として顧客が給与システムで確認した実額を採用。実額がどうしても取れない場合のみ他月と同額で補完する（全月在籍者に限る）。

### パート時間の換算（FTE）と、ツール出力の不一致

- パート等の非フルタイム従業員は正社員の就業時間に換算して人数を出す（例：20÷40=0.5人）。
- 労働時間が取れないとき、ツールは FTE=1.0 にフォールバックして警告を出すが、これは**原則と正反対の暫定値**（過大計上 → 1人当たり給与が過小 → 計画値が下振れ）。全月在籍の非フルタイム者で時間欠落なら、提出前に必ず顧客へ再依頼して埋める。
- 雇用形態が空欄の従業員は正社員既定となり、警告なしで FTE=1.0 になる点に注意。
- 時間欠落者がいる案件では、申請書のR215（1.0換算）と添付の給与計算シート（0換算で母数から脱落）が同一成果物内で食い違うことがある。両出力のFTE一致を提出前に確認する。

### 事務局未確認のグレー解釈（★グレー）

- ★グレー 「従業員はいるが全員が在籍12ヶ月未満で算定対象0名」のケース：給与支給総額・従業員数を役員報酬・役員数ベースで算定した運用例があるが、公募要領・マニュアルの役員読み替え特例は「従業員を雇用していない法人」が条件で、この中間ケースへの明文がない。ツールは自動代入せず警告で人手判断に倒すのが安全側。事務局確認が確実。
- ★グレー 賞与のみ受給者（全月0円＋賞与あり）の除外：「全月分の給与等を受けた者」に非該当という読みで除外しているが、公募要領は算定対象の給与等に賞与も明記しており解釈にグレーが残る。事務局未回答。賞与のみ受給者が実在する案件では優先確認。
- ★グレー 賞与の年度帰属：対象事業年度分のみ R216 に算入（窓補正）しているが、賞与の年度帰属を直接定める明文は公募要領になく、事業年度単位の算定構造からの解釈。R216実績の正式ソースは、法人＝勘定科目内訳明細書（役員報酬手当等及び人件費の内訳書）、個人事業主＝確定申告書の事業所得欄＋賃金台帳。支給日のない賞与・非暦年決算では、各賞与回の支給年月または勘定科目内訳明細書を顧客に求めれば帰属を確定できる。
- ★グレー 決算月を変更した案件：登記等の証明書と申請情報の決算月が一時的に不整合になり不備返却される懸念。予防策として決算月変更の理由書（リリース）を「その他資料」に先回りで添付し、変更届の届出日・受付日を事前に押さえる。ただし「不備返却リスクが高い」自体は支援事業者の予防的判断であり、事務局見解として確定したものではない。
- ★グレー 派遣業など勤務地が事業所所在地と異なる場合：加点判定で比較する地域別最低賃金を、勤務地基準にすべきか事業所所在地基準にすべきかが論点になりうる（要確認）。就業地の最賃が事業所所在地より高い地域だと、事業場内最低賃金の評価に影響する可能性がある。

### 従業員数ヒアリングの概念整理

誤回答が起きやすいので事前に共有する：

- 「正規雇用」は役員を含まない。
- 「その他」は日雇い等の特殊雇用。
- 基本情報の従業員数（現在）と財務情報の従業員数（前事業年度）は別物。期中入退社により人数が違うことがある。
- （実例として、全員数を「その他N名」と誤回答するケースがあった。）

### 事務局へ照会する文面の作法

- 公募要領の該当ページ・項記号は申請枠の版によって異なる（給与支給総額・従業員数の算定ルールは通常枠版とインボイス・セキュリティ枠版でページと項記号が違う）。
- 事務局へ送る文面では、枠（版）と項記号を明記し、交付申請マニュアルは改訂版日付を併記する。
- ページ番号は紙面の印字ページ基準。社内知識ベースの行番号を公募要領ページと取り違えないよう区別する。

### 加点①の提出運用（要件ではなく自社運用）

- 加点①の「30%以上が3か月」は、公募要領上 **連続不要＝判定期間（令和6年10月〜令和7年9月）内で任意の通算3か月**でよい（公式①シートに「任意の３か月」明記）。判定期間は暦の固定窓で、会社の事業年度・決算月では動かない。
- 自社は運用として **連続した3か月・公式様式のExcelのまま**提出している（見やすさ・事務局の原本照合のしやすさのため）。これは自社の好みであって要件ではない。
- **決算月が9月以外だと判定期間が事業年度をまたぐ**（例：ある8月決算の案件では、令和6年10月〜令和7年8月＝前期＋令和7年9月＝今期）。①シートは1枚で、前期・今期の賃金台帳を2冊またいで疎明添付してよい。台帳1冊で連続3か月を綺麗に収めたいときは前期側に収まる連続3か月を選ぶ。制度根拠は [02 制度知識ベース](02_制度知識ベース.md) の加点措置①。

## 3. ツールの不具合・改善から得た教訓

過去のフィードバックで判明した不具合パターンと対処。再発時の切り分けに使う。

- 数値コピペ時の前後半角スペース：ツール出力Excelの数値セルをコピペすると前後に半角スペースが入り、申請フォーマット貼付時にエラーになる事象があった。原因は値の文字列化ではなくテンプレの表示書式（番号書式の幅調整スペーサ）。決算書由来の数値（給与支給総額・人件費・売上・営業利益・粗利・労働生産性等）で起きやすい。書式スペーサ除去で解消。
- 事業内容255字がツールと食い違う：AIがヒアリングの「申請ツール名」欄を読まず、ツール名が見積書のみ由来で見積なしだと空欄になり、AIが別ツールを創作したのが原因。対策はヒアリングの導入ツールをプロンプトに反映しツール厳守を指示すること。
- 賃金台帳一覧に賞与が乗らない：年間合計に賞与が乗らず、賞与込みの正しい給与支給総額（R216）が備考にしか出ず、申請書より少ない値に見える事象。原因は賞与の支給月不明時に月次セルへ振れない意図的設計。重要数字が備考に埋もれるのは混乱の元なので、年間賞与列・給与支給総額（賞与込）列を追加し合計＝R216一致にした（支給月不明の警告は維持）。
- 警告が多くて把握しづらい：よくある警告を番号化（W-XXX 形式）してマニュアル一覧から引けるようにすると運用参照性が上がる。「番号が出たらこれをチェック」という対応が可能になる。
- 「従業員数や金額が実際と違う」という指摘：古いバージョンの出力が原因のことがある（0円月除外の改修前など）。まず使用バージョンを確認し、最新版で再生成すると一致するケースがある。
- 再現できない不具合：Excelのセル結合で数字が入らない/出力先セルがずれる等は、再現できる実物（崩れた出力Excel・元の入力一式・申請枠・決算月・AI版か通常版か）がないと原因特定に着手できない。報告を受けたら現物の提供を依頼するのが最短。全テンプレをスキャンして該当行に結合がないことが確認できれば現テンプレ正常と切り分けられる。
- Drive自動保存が毎回エラー：サービスアカウントの保存先フォルダ権限不足が根本原因のことがある（閲覧者のみで投稿者でない等）。年度フォルダ新設時に同じ共有設定漏れが再発しうる。
- 加点②シートの最賃が古い：地域別最低賃金は毎年10月改定のため、改定期をまたぐ案件で内蔵最賃マスタが前年度（改定前）のままだと、直近月に適用すべき改定後の値が反映されず先方指摘につながる。改定後は内蔵マスタの版を必ず確認する（毎年の定期更新は [06 運用ルールと体制](06_運用ルールと体制.md) の年次更新節）。

## 4. デジタル化セカンドオピニオン加点の実務（第3次公募〜）

第3次公募回（2026/6/16〜）から開始・適用された加点措置。賃金台帳の外の加点で、ツールの自動判定対象ではない。以下は制度・手続きの事実のみ（自社の営業戦略・プロダクト比較は本ファイルに含めない）。

### 対象と登場人物

- 対象は**通常枠のみ**。インボイス枠・セキュリティ枠・複数社連携枠は対象外。送客・案内時に必ず枠を確認する。
- 面談相手の「確認者」は、中小企業診断士またはITコーディネータの資格を持ち、募集を経て事務局に登録された第三者。事務局そのものではない。確認者が面談結果をシステムに登録し、それを見て事務局が加点審査を行う。

### 面談の条件

- 出られるのは**経営者本人のみ**（法人は代表取締役、個人事業主は本人）。代理出席は即不成立。
- ITベンダー・IT導入支援事業者（販売した代理店を含む）は**同席不可**。社内のデジタル化責任者など社内関係者の同席は可。
- オンライン（Zoom）で1対1、所要は概ね30〜60分（面談自体は1時間）。カメラON必須、録画への承諾が必要。
- 確認者への連絡はキャンセル打診以外NG。予約・日程確定等のやり取りは申請者本人が行う。不適切対応には事務局の通報窓口がある。

### タイミング

- 面談は申請する公募回の申請締切までに済ませる必要がある。
- 締切2週間前は確認者予約が混雑するため、予約フォーム送信（日程調整依頼）は締切から逆算して早めに行う。
- 実フォームでは面談希望日時は各回2時間以上の幅で第1〜第3希望が必須（最大10件）。経営者本人が出られる候補日時を3つ以上確保する必要がある。

### 評価の視点（2軸）

確認者は2軸で評価する：

1. 取組内容の整合性・論理性：現状課題 → 導入ツール → 効果 → 将来像が一本の線でつながり、目的が明確で申請内容と矛盾せず、スケジュール・体制に現実味があるか。
2. 経営者の理解度・意欲：自分の言葉で説明でき、現場任せ・ベンダー任せでなく、導入後も継続関与する意思があり、AIも積極活用する姿勢があるか。

評価の肝：取組が高度である必要はなく、**自社にとっての必要性を経営者が自分の言葉で語れること**が重視される。AI生成の下書きを棒読みすると評価軸②で失点する。投資回収（費用対効果＝この投資でどれだけ時間・コストが浮くか）を経営者が自分の言葉で語れると、評価軸①（取組の整合性）にも②（理解度・意欲）にも効く。評価結果・採否理由は申請者に非開示なので、改善ループが回らない。事前のチェックリスト・想定問答で品質を前倒しに担保する運用が要る。

### 手続きの流れ

- 顧客側の段取り：申請マイページ →「デジタル化セカンドオピニオン予約（加点措置）」→ デジタル経営ビジョン入力 → 確認者を都道府県・得意業種で検索して選択 → 希望日時を第1〜第3希望必須（最大10）で送信 → 確認者が日程確定 → 確定メールのZoom URLで面談。
- 申請者情報の業種欄は、確認者を得意業種で検索するのに用いる。

### 面談前に入力する「デジタル経営ビジョン」7項目

予約フォームで入力する（実申請フォームの①〜⑦と1:1で一致）：

1. 現状把握（主要業務のデジタル化状況を5つ以上＋利用中の生成AIツール。未使用なら「今回が当社初の生成AI導入」と明記する＝今年からAIの有無が加点対象なので、未導入はむしろ明確に書くほうが有利）
2. 将来目指す姿
3. 本申請の目的＋ITツールを選んだ理由
4. スケジュール（導入前/直後/1年後の活用、想定課題と対応策）
5. 体制整備（経営者とデジタル化責任者の氏名・役割）
6. 経営者の関わり（**プルダウン5択**。基本は最上位「経営者が積極的にデジタル化に関わり、経営戦略として推進している」を選ぶ＝評価軸②に直結。1〜4は関与が弱く加点上不利。実態がそこに届いていない場合も、面談前に経営者本人がこの姿勢で臨めるよう合意・準備する）
7. その他

### 準備運用のコツ

- 7項目は、営業が経営者に直接ヒアリングして集める運用が現実的。詳細な事前シートを顧客に細かく記入させる（特に活用例5つ以上）のは記入負荷が高いため、選択肢チェック中心のヒアリングで拾う方が回りやすい。
- 申請書（事業内容・本申請の目的）の記載と面談での発言が矛盾すると不加点リスク（評価軸①②に直結）。予約フォーム入力説明の場でヒアリングシートを作りながら、申請内容と面談発言の整合性を確認する運用が有効。

### 面談準備の配布物テンプレ（同梱）と使い方

この加点の面談準備を回すための配布物テンプレを、本パックに同梱している（`docs/セカンドオピニオン加点/配布物テンプレ/` と `_sample/`）。汎用（ツール中立）版のみで、自社製品特化版・社長方針・議事・案件別は含めていない。使う順序と責務：

- **予約フォームの欄定義の「正」**：`00_予約フォーム仕様.md`（①〜⑦の実フォーム欄構造。生成物と食い違ったらこれを優先）。
- **営業が経営者に聞く**：`05_面談ヒアリングシート.md`（紙）／`05_面談ヒアリングシート_オンライン版.md`（チェックリスト）。事前に渡す予告は `05_別紙_お客様向け事前案内.md`、営業側の狙い・NG発言の言い換えは `05_別紙_営業向けカンペ.md`。
- **電話で深掘り**：`07_電話ヒアリング質問シート.md`（①〜⑦に1:1対応・優先度◎○△）／操作用は `07_電話ヒアリング質問シート_操作用.md`。
- **入力文を生成**：`06_入力整理プロンプト.md`（05＋07の回答→予約フォーム入力文①〜⑦を生成する全社標準プロンプト）。案件固有の想定問答骨子は `06b_面談準備メモ生成プロンプト.md`。
- **面談の想定問答・記入見本**：`08_面談回答例_汎用中立版.md`／経営者に渡すクリーン版 `10_経営者向け_一問一答の回答例_汎用.md`。到達イメージの品質ベンチマークは `14_記入見本_予約フォーム入力_製造業例.md`・`15_記入見本_経営者一問一答_製造業例.md`、粒度をつかむダミー例は `_sample/05_記入サンプル_ダミー工務店.md`・`_sample/07_記入サンプル_情報少なめ_ダミー工務店.md`。

ヒアリングは2経路：**お客様確認メール（メイン）** を送って回答をもらい、返信が無ければ **電話でフォロー**する。メール下書きは `07b_お客様確認メール生成プロンプト.md` で生成する。社外に出す文面には **加点／減点／評価／優先度／規程数値／⑥の選択方針** などの内部語を書かない（「確認者」も「社外の専門家」等に言い換える）。

生成プロンプト運用のコツ：**創作禁止**（分からない項目は `(要確認)` で残す）、**投資回収（費用対効果）の筋**を通す、同一ツールでも自社に即した差別化を書く、**顧客名・実数値はプロンプトに書かず資料側（git管理外）に閉じる**。
