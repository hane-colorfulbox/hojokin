# 補助金 業務フロー全体マップ（時間軸 × 取得情報 × 担当作業）

デジタル化・AI導入補助金（旧IT導入補助金）の申請支援業務を、制度に沿った**普遍的な工程**で俯瞰する地図。1申請回の時間軸に沿って、各工程で **何を取得し / どの担当が何をし / 何が成果物で / どこで事故るか** を1枚に束ねる。

読み方（この地図の設計方針）:

- **本文＝普遍的な流れ**。制度・工程・取得情報・担当機能で書く。制度改定やツール入れ替えがあっても骨格は変わらない。
- **`> 実装メモ:` ＝現行の具体実装**（ツール名・画面名・タスク名・スクリプト・バージョン・URL）。ここは**変わり得る前提**で読む。固有の実装は末尾[8. 現行の実装レイヤ](#8-現行の実装レイヤ変わり得るもの)に集約した。
- **担当は機能ロールで表記**（誰が担うかは社内で割り当て）。個人名・顧客名・金額実数は載せない（このファイルは共有・git 追跡を前提とする）。
- **日付は相対（D-day）**で書く。絶対日は申請回ごとに引き直す。
- 制度の数値（閾値・率）は「ルール＋現行値」で書く。公募要領の改定時は現行値だけ差し替える。

最終更新: 2026-07-21

## 0. 全体像（1枚で）

補助金の申請支援は **3本のトラックが並走** する。メインの申請フローに、2種類の加点が乗る。

```
[メイントラック] 申請 〜 交付 〜 実績報告
 送客 → 案件セットアップ → 資料回収 → 書類作成 → 交付申請 → 交付決定 → 実績報告 → 交付
                              │            │
                              │            └─[加点A] 賃上げ加点（補助率引上げ・加点措置）
                              │               書類作成〜交付申請に内包。専用台帳 → 判定 → 提出シート
                              │
                              └─[加点B] 面談型加点（デジタル化セカンドオピニオン／★通常枠のみ）
                                 事前ヒアリング → 情報整理 → 経営者の準備 → 予約 → 経営者×第三者の面談
                                 申請締切から逆算して並走。支援者は面談に同席できない＝事前に仕込む
```

登場ロール（機能で定義。担当者の割り当ては社内で決める）:

| ロール | 機能 |
|---|---|
| 申請者（経営者） | 資料提出・ポータル入力・提出・面談本人。**支援者は代理申請しない** |
| 支援事業者・営業 | 送客・初回対応・ヒアリング。面談型加点の面談には**同席不可** |
| 窓口担当 | 依頼・事務局照会の**一本化**（社内外の連絡はここに集約し混乱を防ぐ） |
| ツール連携担当 | 自動化の実装・本番反映・API連携 |
| AI実務担当 | AIを使った資料抽出・書類生成・台帳変換・加点判定・文面生成・検算。**面談は非同席の裏方** |
| 自動化基盤 | 送客フォーム→管理表/ストレージ、受信メール添付の自動格納、書類生成ツール |
| 事務局 | 交付審査。制度解釈の照会先（窓口担当経由） |
| 確認者 | 面談型加点の面談相手（登録された社外の専門家）。**顧客向け文面では「社外の専門家」と表現** |

## 1. 時間軸（1申請回のライフサイクル）

締切（申請提出＝D-0）からの逆算。**相対関係だけが普遍**で、絶対日は回ごとに設定する。

| 相対日 | イベント | 主な動き |
|---|---|---|
| 定例（月次） | 社内定例MTG | ツール改善・運用変更の進捗共有。次サイクルの起点 |
| D-21目安 | 資料依頼開始 / 面談型加点の予約送信SLA | 顧客へ資料依頼。加点B対象は**この頃までに予約送信**（締切2週前は面談枠が混雑） |
| D-18〜14 | 面談型加点の面談実施 | 経営者×確認者（経営者が出られる日を最優先確保） |
| D-12目安 | 疎明期限 | （運用フェーズ。詳細は運用マニュアル側） |
| D-7目安 | 資料提出期限 / 申請内容の最終確認 | 賃金台帳の回収・変換・検算をここまでに完了 |
| D-0 | 申請締切 | 交付申請を提出。面談は締切までに済ませていること |
| 提出後 | 交付決定（採択/不採択） | ステータス更新 → 実績報告フェーズへ |

> 実装メモ: 直近回では 資料依頼〜締切 を約2週間で回した（推奨送客 → 疎明 → 資料提出 → 申請締切）。社内定例は毎月25日。過去回の絶対日は固定値として使わない。

制度で固定された時間窓（会社の決算月に依らず不変）:

- 賃上げ加点①の判定窓＝**前年度10月〜当年度9月の暦月固定**＋交付申請直近月。判定に使う3か月は**連続不要＝任意3か月**。
  - > 実装メモ: 現行制度では 令和6年10月〜令和7年9月。
- 賃上げ加点②＝基準月（当年度の指定月）と直近月（交付申請月の前月）を比較。
  - > 実装メモ: 現行制度では 基準月＝令和7年7月、直近月＝交付申請月の前月。

年次イベント: **毎年10月に地域別最低賃金が全国改定**。加点判定はこの最賃で行うため、改定後すみやかにマスタを更新する（[7. 定期・年次のリズム](#7-定期年次のリズム)）。

## 2. メインフロー: 送客 〜 書類作成 〜 交付申請

### 2-1. 送客・案件セットアップ

| 項目 | 内容 |
|---|---|
| タイミング | 案件の起点 |
| 取得情報 | 送客フォーム: 企業名・申請枠（通常枠/インボイス枠 等）・支援事業者名・連絡先 |
| 担当作業 | 自社作業なし（自動化基盤が処理）。通知で送客を把握する程度 |
| 成果物 | 案件管理表への転記、顧客フォルダ自動作成、担当・ステータスの初期設定、送客通知 |
| 注意 | フォーム経由でないと通知・フォルダ連携が付かないことがある |

> 実装メモ: 送客フォーム→案件管理スプレッドシート／Google Drive の顧客フォルダ（`1.交付申請`/`2.実績報告`）自動作成、「補助金連絡」スペースへChat通知。同名再送でもフォルダは重複作成されない。

### 2-2. 進捗管理（ステータス）

- **担当作業**（窓口/実務担当）: 案件管理表のステータスを進行に合わせて更新。
- **ステータスの流れ（一般形）**: 初回案内 → 資料待ち → 準備中 → 準備完了 → 申請済 → 交付決定 → 実績報告 → 交付済。

### 2-3. 資料回収

| 項目 | 内容 |
|---|---|
| タイミング | 資料待ち〜準備中 |
| 取得情報（回収物） | ヒアリングシート（申請書の大部分の源泉）／登記事項証明書（**取得3ヶ月以内・全ページ**）／納税証明書／決算書（損益計算書 直近2期）／賃金台帳（直近12ヶ月）／ITツール見積書。加えて 電子申請ID（gBizIDプライム）・セキュリティ自己宣言の有無 |
| 担当作業 | 揃い具合をチェックし不足を洗い出す。ファイル名に会社名を入れておく（抽出時の会社判別のため） |
| 注意 | 回収は**原則 Excel/CSV**（形式統一で自動化精度が上がる・コスト減）。PDFしか出ない場合は[3. 賃金台帳の回収・変換](#3-サブフロー-賃金台帳の回収変換)へ |

> 実装メモ: 受信メール（ラベル「補助金_受信」＋添付）は約15分間隔で該当フォルダへ自動格納（件名・送信元で振り分け）。

### 2-4. 書類作成

回収資料をAIで抽出し、申請テンプレートへ転記する。**決算月の確定が前提**（賃金台帳の対象12ヶ月を決めるため）。個人事業主は決算月を暦年末に固定し役員セクションを持たない等、法人と挙動が異なる。

書類作成は概ね3つの生成に分かれる:

| 生成物 | 取得情報（入力） | 担当作業 | 成果物 |
|---|---|---|---|
| 申請書 | 会社名・枠・決算月＋ヒアリング/登記簿/PL/見積/賃金台帳 | 枠と決算月を指定し資料を読ませて生成。AIが各書類を抽出し転記 | 申請書一式（基本情報・役員・財務・経営状況・賃上げ計画・転記用テキスト） |
| 給与支給総額計算 | 賃金台帳（直近12ヶ月）・PL・給与明細 | 従業員別・月別を集計。役員報酬を控除、パートをFTE換算 | 給与支給総額（R216）、賃上げ3年計画（規程の年率以上） |
| 賃上げ加点判定（該当案件のみ） | 都道府県・**交付申請月**・生の賃金台帳 | [4. 賃上げ加点](#4-サブフロー-賃上げ加点)の2工程 | 加点①/②の提出シート・対象可否 |

**目視確認（必須ゲート）**: AI抽出値、特に**金額と日付**を必ずチェック。従業員数・PL金額・1人当たり給与支給総額・賃上げ計画・加点対象者。最賃ギリギリ層・加点狙い案件は**原本照合**（抽出精度が補助率を左右する）。空欄は確認項目としてメモ→手入力。

> 実装メモ: 本番は書類生成ツール（現状 Streamlit Cloud 運用、URLは[8章](#8-現行の実装レイヤ変わり得るもの)）。決算月未選択だと実行不可（加点判定タスクのみ決算月不要）。テンプレ原本は改変せず自動でコピー処理。AI抽出＝Sonnet系＋画像、文章生成＝Opus系（フラグで切替可）。結果を案件フォルダへ自動保存するオプションあり（書き込み権限が要る）。

### 2-5. 交付申請（マイページ入力〜提出）

書類完成後、申請者の電子申請IDでマイページに入り、画面共有しながら入力。**入力主体が ①申請者 → ②支援事業者 → ③申請者 とバトンタッチ**し、最後に本人認証で提出。**①の「入力完了」後は編集不可**（引継ぎ前の再確認が必須）。

| フェーズ | 主体 | 主な入力・支援 |
|---|---|---|
| 事前準備 | 支援＋申請者 | セキュリティ自己宣言ID・事前診断の結果・添付書類（登記/納税証明/PL）を揃える。台帳変換出力を用意し提出前検算に備える |
| ① 類型・基本情報 | 申請者（実務担当が素材提供） | 業種・**事業内容（規定字数）**・役員（登記と照合）・従業員数・加点項目。数値/文章は1つずつ渡してコピペ（入力ミス防止） |
| ① 財務情報（前年度）★ | 申請者 | 従業員数（雇用形態別）・年間平均労働時間・売上/利益/減価償却/人件費。**R215/R216の前提値**。台帳変換の数値と齟齬が出ないよう照合 |
| ② 導入ツール登録 | 支援事業者 | 導入ツール・価格・数量、補助金申請額を確定。金額サマリを申請者と読み合わせ |
| ③ 宣誓・計画数値 ★ | 申請者（実務担当が検算） | 事業場内最低賃金・給与支給総額テーブル（前年度＋計画1〜3年目）→年平均成長率。R216対象者の線引きを確認 |
| ③ 労働生産性指標 | 申請者 | **★通常枠でのみ追加**（営業利益・人件費・減価償却費・総労働時間の3年計画）。インボイス枠には無い |
| ③ 賃上げ表明・提出 | 申請者 | 賃上げ幅（ヒアリングから転記）・表明方法/日付/表明先。最終確認→本人認証で提出 |

**当日提出できない場合**: 入力内容は保存される。後日マイページから該当画面まで進み、差し替え／認証→提出。添付必須欄は空だと進めないので、書類未取得時は前回分で仮添付し後日差し替え可。

> 実装メモ: 電子申請ID＝gBizIDプライム。本人認証＝SMS（コードは発行30分以内に提出）。事前診断＝IT戦略ナビwith。添付は各10MB未満・jpg/png/pdf。

### 2-6. 事務局照会・制度解釈

- **担当作業**（実務担当→窓口担当）: 公募要領・交付申請マニュアル・実機を原本照合し、事務局照会文と社内依頼文を起案。引用は枠（版）とページ・項記号を明記。
- **注意**: 連絡は**窓口担当に一本化**（事務局照会も窓口経由）。事務局の明示回答が未取得の論点は、最終判断を原本・実機で確認してから確定する。

### メインフローの落とし穴

- フェーズ①「入力完了」後は編集不可でフェーズ②へ引き継がれる（**後戻り不可**）。引継ぎ前に読み合わせる。
- 従業員数の三重の混同: 「正規雇用」は役員を含まない／「その他」は日雇い等／**基本情報の人数（現在）と財務情報の人数（前事業年度）は別物**（期中入退社で違う）。
- 給与支給総額（R216）の対象者＝前事業年度に全月分給与を受けた者のみ。金額は**総支給（課税支給合計）**であって手取りではない。口語で呼び替えると違う列を拾う。
- 支援者は代理申請しない。最終のポータル入力・提出は申請者本人。

## 3. サブフロー: 賃金台帳の回収・変換

給与支給総額（R216）・従業員数（R215）の入力になる賃金台帳を集め、**ツールが読める規格に整える**。この台帳の質が補助率・算定精度を左右する。

### 回収と経路分岐

1. **回収依頼は原則 Excel/CSV**（窓口担当経由）。対象＝直近事業年度の12ヶ月分。決算月・法人/個人の別も確認。
2. 形式で経路を分岐（**2026-07-21 の3次振り返りで序列を反転＝ローカル標準**）:
   - Excel/CSV → そのまま投入。
   - PDF → **経路1: ローカル変換（Claude Code＋スキル。標準・精度優先）**。手書き・画像PDFも対応。出力には確認用の「原本転記」シート群（PDF全ページ・全項目の転記。通勤手当等の関数計算・加点判定への転用可）が付く。
   - **経路2: 自動変換ツール**（速さ優先時・Claude Code 環境が無い/不慣れなときの代替）。
   - 自動化ツールを提供していない外部先 → **変換用プロンプトを共有**。
3. 経路1と経路2は**独立実装だが出力規格は同一**。規格（列・補助金ルール）を変えたら**必ず両方を同期**（片方だけ直すと産物が読めない）。

### 規格の要点（列と値のルール）

- 列: No／氏名／雇用形態（正社員・パート・役員）／月間平均時間（★パート必須・FTE換算用）／時給（★パート必須）／1〜12月の課税支給合計／年間通勤手当／年間賞与。
- 検算: 機械検算（社員別年間合計・月別全社計・原本総合計突合・通勤手当S列の整合＝控除漏れと二重控除の両方向）→ 最終ゲートで R216 を逆算検証。最賃ギリギリ層は原本照合。

> 実装メモ: 規格テンプレ＝`ツール/賃金台帳テンプレート.xlsx`（B6以降がデータ行）。経路1＝`wagebook-convert` スキル（出力の「原本転記*」シート群はツールのリーダーが名前ガードで読み飛ばす。v0.2.91〜。全項目・ページ別化は 2026-07-26〜）。経路2＝ツール「賃金台帳の作成」タスク。外部プロンプト＝`docs/外部クライアント向け_賃金台帳集計/転記プロンプト.md`。機械検算＝`review/verify_wagebook.py`（API不使用）。

### 賃金台帳の落とし穴（多くは制度ルールなので普遍）

- **月列＝直近事業年度の12ヶ月**（暦年1〜12月ではない）。決算月ズレで各月を正しい月位置に置く。**空欄月があっても後続を詰めてずらさない**（左詰めズレは年間合計検算では捕まらない＝月単位検算が必須）。
- **通勤手当は課税・非課税を問わず控除**（2026-07-27 運用）。ただし通勤手当欄（S列）に入れるのは「**月列の値に含まれている通勤手当の年額**」。月列が課税支給合計で通勤手当が非課税処理済みなら**空欄**（埋めると基本給を削る＝最頻出事故）。含まれているなら年額を入れる。判定は「課税支給額 ＝ Σ支給項目（通勤手当を含む）」が成り立つかで機械的に決まる。
- **賞与は月セルに混ぜず年間賞与欄**へ。支給年月が不明で確定できない時は**推測確定禁止**（暫定＋要確認）。
- **役員ラベル正規化**（代表取締役/取締役/監査役/理事長/理事/監事→「役員」、個人事業主の事業主→役員、専従者→従業員）。未正規化だとR216に誤算入。
- **パートの月平均時間が空欄だとFTE=1.0でサイレント昇格**しR215過大。パートは時間・時給必須。
- **支給のない月は空欄（0禁止）**。0は中途入社/退社/休職を意味し誤判定を招く。ただし窓ズレで1ヶ月欠けただけの全月在籍者は中途扱いにしない。
- 採用金額は**課税支給合計**で固定（総支給/差引支給でない）。迷ったら「給与所得として課税対象か」で判断。そこに含まれている通勤手当は S列で控除する。

## 4. サブフロー: 賃上げ加点

交付申請フェーズで、賃金台帳から「補助率引上げのトリガー（加点①）」と「加点措置（加点②）」を判定し、公式の賃金状況報告シート①②を作る。

### なぜ専用台帳か

通常の給与支給総額用台帳（総支給ベース）では判定できない。加点は**時間換算給与＝基本給÷月間所定労働時間**（残業・通勤・精皆勤・家族手当を除く所定内賃金）を**暦月固定窓**で見るため、基本給・所定労働時間・暦月固定列を持つ**専用台帳が必須**（総支給台帳だと正社員が判定からこぼれる）。

### 2工程

| 工程 | 担当作業 | 成果物 |
|---|---|---|
| ① 専用台帳の作成 | 生台帳を投入し、基本給・月別所定労働時間を抽出 | 加点判定用台帳（列見出しは暦月固定） |
| ①後の人手補完 | 所定労働時間が取れない月給者に会社の月平均所定労働時間を手入力、時給者は月別労働時間を補入力、基本給空欄月を原本補完 | 確認・補入力済みの台帳 |
| ② 判定 | 交付申請月を入れて判定（決定論・**AI課金なし**） | 加点①②の対象可否＋公式報告シート①② |

> 実装メモ: PDF 台帳の案件は Claude Code の `katen-judge` スキル（引き継ぎパック同梱）で①→②→公式シート生成まで**ローカル完結**（2026-07-21〜）。ツールの工程①は PDF 未対応のため Excel 入力用。実行チェックリスト＝`docs/チェックリスト_加点判定.md`。

### 判定条件（ルール＋現行値）

- **加点①（補助率引上げ）**: 暦月固定窓で、時間換算給与が「改定後の地域別最低賃金 未満 かつ >0」の従業員が全従業員の**規定割合以上ある月が規定か月数以上**あれば補助率引上げ。この規定か月は**連続不要＝任意**。
  - > 実装メモ: 現行＝30%以上の月が3か月以上（連続不要は2026-06-25合意・公募要領p.18）。
- **加点②**: 直近月の事業場内最低賃金 − 基準月の事業場内最低賃金 ≥ **規定額** なら対象。
  - > 実装メモ: 現行＝63円以上（公募要領p.26）。事業場内最低賃金＝時間換算給与列のMIN。

### 提出シート

- 加点①シートは**申請枠で1枚**（通常枠とインボイス/セキュリティ枠で様式・データ開始行が異なる。1枚だけ出力）。
- 加点②シートは全枠共通。
- 決算月が窓の末尾（現行なら9月）以外だと加点①の窓が事業年度をまたぐ→**シートは1枚のまま、台帳2冊（前期・今期）を疎明資料に添付**。年度ごと2枚は不要。

### 加点の落とし穴

- 抽出精度が補助率を左右する。生成台帳は提出前に必ず人手確認（最賃ギリギリ層は原本照合）。ツールの最賃割れ警告は安全網に過ぎない。
- 加点②は交付申請月の入力が必須（未入力だと判定不能）。
- 「連続◯か月・そのまま提出」は自社の見やすさ運用であって**要件ではない**（要件は任意◯か月）。
- 役員は判定母数から除外。

## 5. 並走トラック: 面談型加点（デジタル化セカンドオピニオン／★通常枠のみ）

**経営者本人**が登録された社外の専門家（確認者）と**オンライン面談**し、取組の整合性と経営者の理解度・意欲の**2軸**で評価される加点。**支援者（ベンダー・代理店）は面談に同席できない**＝当日助けられないので、**事前に仕込み切る**のが勝負。

### 制度の要点

- 対象＝**通常枠のみ**（他枠は対象外）。導入ツールがAI搭載だと枠を取り違えやすい→**着手前に「通常枠で出す」を窓口担当経由で1点確認**（枠違いだと作業が空振り）。
- 面談＝オンライン・約1時間・**カメラON・録画あり**・経営者本人（代理は即不成立、社内のデジタル化責任者の同席はOK）。
- 面談前に予約フォームで**デジタル経営ビジョン7項目**を入力（①現状把握＋利用中の生成AI ②将来像 ③目的＋選定理由 ④スケジュール ⑤体制＝デジタル化責任者 ⑥経営者の関わり ⑦その他）。
- 評価結果・採否理由は**非開示**。確認者への連絡はキャンセル打診以外NG。

### 運用フロー（顧客接点の順序 × 時間軸）

```
事前ヒアリング（営業が経営者に直接。事前案内を渡す）
   → 確認メールで不足項目を回収（返信なければ電話フォロー）
      → 実務担当が「予約フォーム入力文」＋「経営者向けカンペ」を作成
         → 予約フォーム入力説明MTG（面談担当×経営者。読み合わせ＝面談準備を兼ねる）
            → 申請者が予約送信・確認者選択・希望日時（★D-21目安まで）
               → 経営者×確認者の面談（★D-18〜14）
                  → 申請内容の最終確認（D-7）→ 申請（D-0）
```

- 予約送信の社内SLA＝**申請締切 D-21目安まで**（締切2週前は面談枠が混雑）。
- 面談候補日は**幅を持たせて複数（本人が出られる日時）**必須。

### 情報整理の要点（支援者側で作るもの）

支援者が作るのは大きく2つ。**面談当日は本人しか出られない**前提で、事前に本人が語れる状態にするための素材:

1. **予約フォーム入力文**（デジタル経営ビジョン7項目の下書き。フォームに貼れる文章。冒頭に「確認者に伝えるポイント」、末尾に「※下書きです。ご自身の言葉に直してください」）。
2. **経営者向けカンペ**（想定問答＋回答例。汎用版と、導入ツール特化版）。

作る際の原則:

- **無い数字・無い痛み・無い取り組みは作らない**（空欄は「要確認」で返す）。規程の目標数値は本人に聞かず、規程に沿って支援側で付与。
- 選定理由の**顧客向けNG＝「業者・営業に勧められた」「補助金が出るから」**（面談で最も減点）。自社起点の決め手（連携/価格/サポート/操作性/同業実績/機能適合）に言い換えて1つ以上拾う。
- 「経営者自身の関わり」を問う設問が最重要。「担当/業者に任せている」は最大の減点。
- 申請書は字数が限られ差別化しにくい＝**面談でこそ差別化**（顧客メリット）。

### 顧客向け文面のNGワード（確認メール・事前案内・カンペ共通）

加点／減点／評価／審査／優先度ラベル／規程数値／⑥選択方針／「確認者」（→**社外の専門家**）／「ベンダー」／「AIで生成」（→**当社でたたき台をお作りします**）／投資回収・費用対効果・回収期間・金額などの社内フレーミング語。足りない項目だけ平易な依頼文に翻訳し、多くても数点・各1行。

> 実装メモ: この加点は**ツール化せず手運用のプロンプト**で回す（毎回のAI課金を避ける）。配布物・プロンプトの番号体系と同期ルールは[8章](#8-現行の実装レイヤ変わり得るもの)。顧客固有情報（顧客名・実数・生成した実物）はマスタープロンプトに書かず案件別フォルダ（gitignore）に閉じる。

## 6. 担当作業チートシート（局面 → 何をするか）

| 局面 | AI実務担当が主にやること |
|---|---|
| 資料回収 | 揃い具合チェック・不足の洗い出し・会社名でファイル整理 |
| 賃金台帳変換 | 形式に応じ経路1/2/プロンプトを選択→規格Excel化→機械検算→R216逆算 |
| 書類作成 | 申請書・給与支給総額を生成→**金額と日付を目視確認**→空欄補完 |
| 賃上げ加点 | 専用台帳作成→人手補完→判定→提出シート確認（原本照合） |
| 交付申請 | 事業内容・数値の素材提供、提出前検算、事務局照会文の起案 |
| 面談型加点 | 予約フォーム入力文・経営者カンペの生成（手運用プロンプト） |
| 制度解釈 | 原本照合→照会文起案（窓口担当経由で事務局へ） |

原則: 「最低限動く」より**本番品質**。生成物は提出前に必ず人手確認。判断が割れる論点は原本・実機で裏取りしてから確定。

## 7. 定期・年次のリズム

- **月次の社内定例MTG**: ツール改善・運用変更の進捗、前サイクルの改善タスクの進捗を報告。
  - > 実装メモ: 現行は毎月25日（補助金TM MTG）。改善タスクは `docs/TODO_2次申請改善.md`。
- **毎年10月 最低賃金改定の反映（年次保守）**: 加点判定は地域別最低賃金で行うため、改定後すみやかに**内蔵マスタを全都道府県で突合更新**する。取りこぼすと古い最賃で資料を出す事故になる。加点②は基準月と直近月で適用最賃の期が変わる点に注意。派遣業など勤務地≠事業所の場合の比較地域は要確認。
  - > 実装メモ: 更新3点＝`config.MIN_WAGE_MAP`（改定後）／`wage_reader.MIN_WAGE_R6`（改定前・加点①下限用）／加点②公式テンプレ内蔵マスタ。全47都道府県で突合。
- **申請回ごとに引き直すもの**: 資料依頼/疎明/資料提出/申請締切の絶対日（相対の逆算枠は再利用可）。
